# Plan: Rewrite `bin/devcontainer` as a Rust binary (`dev-container`)

## Context

The existing `bin/devcontainer` is a bash script managing devcontainer lifecycle (create, edit,
inspect, run, stop, connect, list). It is not fully SPECS-compliant. The goal is to rewrite it
as a standalone, zero-dependency Rust binary named `dev-container`.

SPECS.md is the single source of truth. The bash script is reference material only.

---

## Constraints

- Binary name: `dev-container`
- Zero runtime dependencies (statically-linked where possible, no dynamic libs beyond libc)
- No external crates beyond what is strictly necessary for argument parsing and error handling
- Target: lightest possible binary (`opt-level = "z"`, `lto = true`, `strip = true`)
- Rust edition 2024, version 1.83+ (stable at time of writing)
- Tests are integration/external wrapper tests only (no unit tests)
- A `Makefile` exposes all developer commands

---

## Allowed crates (minimal set)

| Crate | Purpose | Justification |
|---|---|---|
| `clap` (derive feature) | CLI argument parsing | Industry standard, compile-time, zero runtime overhead path |
| `anyhow` | Error propagation in application code | Reduces boilerplate, application-level only |

No async runtime. All I/O is blocking. No `serde`, no `tokio`, no `reqwest`.

## Module responsibilities

### `cli.rs`

Defines the complete CLI surface using `clap` derive macros:

```
dev-container <COMMAND>

Commands:
  new      <name> [-f/--force]
  edit     <name> [-c/--compose] [-q/--no-reload]
  inspect  <name>
  run      <name> [-s/--ssh-key <path>]
  stop     <name> [-d/--detach] [-f/--force]
  connect  <name> [-s/--ssh-key <path>]
  list
  version
  help     (auto-generated by clap)
```

Key differences from the bash script CLI:
- `run`, `stop`, `connect` take `<name>` as a positional argument, not `-p <name>`
- `connect` takes `<name>` then resolves host/port from `.env`, not `-h/-p` flags
- `edit` gains `-q/--no-reload` flag (suppress container reload after edit)
- `stop` gains both `-d/--detach` and `-f/--force` flags

### `config.rs`

- `ProjectPaths::resolve(name: &str) -> Result<ProjectPaths>` — builds all paths from `$HOME`
- `EnvConfig::load(path: &Path) -> Result<EnvConfig>` — parses `.env` key=value, skips comments,
  strips whitespace, returns typed struct with all known fields as `Option<String>`
- `validate_project_name(name: &str) -> Result<()>` — rejects empty, rejects chars outside
  `[a-z0-9_-]`
- `project_exists(paths: &ProjectPaths) -> bool`

`EnvConfig` fields:
```rust
pub struct EnvConfig {
    pub user: Option<String>,
    pub user_id: Option<String>,
    pub devcontainer_image_name: Option<String>,
    pub resources_ram: Option<String>,
    pub hostname: Option<String>,
    pub ssh_port: Option<u16>,
    pub enable_ssh: Option<bool>,
}
```

### `docker.rs`

Thin wrappers that build `std::process::Command` invocations and return `Result<Output>`.
No business logic lives here.

- `compose_up(project_name, compose_files, env_vars) -> Result<()>`
- `compose_down(project_name, force, wait) -> Result<()>`
- `compose_config(project_name, compose_files, env_vars) -> Result<String>`
- `compose_ls_json() -> Result<String>`
- `container_id(project_name) -> Result<String>`
- `docker_cp(src, dest) -> Result<()>`
- `docker_exec(container_id, cmd, user) -> Result<Output>`
- `check_docker() -> Result<()>` — verifies `docker` and `docker compose` are available

### `commands/new.rs`

1. `validate_project_name`
2. `project_exists` check — error if exists and `!force`
3. `fs::create_dir_all` for project dir and `volumes/`
4. Write `.env` template (from embedded string literal, matches SPECS exactly)
5. Write `docker-compose.yml` template (extended overlay format, matches SPECS exactly)
6. Print confirmation with created paths

### `commands/edit.rs`

1. Validate name, check project exists
2. Resolve target file (`.env` default, `docker-compose.yml` if `-c`)
3. Open file with editor: try `$VISUAL`, then `$EDITOR`, then `xdg-open`, then error

### `commands/inspect.rs`

1. Validate name, check project exists, check config files exist
2. Parse `.env` with `EnvConfig::load`
3. Call `compose_config` to get merged compose output
4. Print formatted summary: env vars section + compose config section

### `commands/run.rs`

1. Validate name, check project exists, check config files exist
2. Load `EnvConfig`
3. `fs::create_dir_all` for `volumes/<user>` and `volumes/workdir`
4. Build env vars map (`PROJECTS_TOP_DIR`, `PROJECT_NAME`) for compose
5. `compose_up` (detached)
6. Find container id via `container_id()`
7. If `-s <key>`: validate public key format, `docker cp`, `docker exec` to append to
   `authorized_keys`
8. Print startup summary

SSH public key validation: read file, check that first token is a known key type
(`ssh-rsa`, `ssh-ed25519`, `ecdsa-sha2-nistp256`, etc.) using a simple prefix check.
No external crypto library needed.

### `commands/stop.rs`

1. Validate name, check project exists
2. `compose_down(name, force, !detach)`

### `commands/connect.rs`

1. Validate name, check project exists
2. Load `EnvConfig` — warn on missing `SSH_PORT` (use 22224), warn on missing `HOSTNAME`
   (use localhost)
3. Build `ssh` invocation: `-A -p <port> <user>@<host>` or `<host>` if no user
4. If `-s <key>` provided: add `-i <key>` flag
5. `exec`-replace the process with `ssh` using `std::process::Command::exec` (unix only) so
   the terminal is a proper PTY hand-off

### `commands/list.rs`

1. `check_docker()`
2. `compose_ls_json()` — parse JSON output manually (no serde) using string search or a
   minimal hand-rolled parser for the known schema
3. Read all subdirs of `PROJECTS_TOP_DIR`
4. For each project: load `.env`, cross-reference with running compose projects for status
5. Print table with columns: `NAME`, `STATUS`, `SSH_PORT`, `IMAGE`

Table rendering: hand-rolled, compute column widths from content, pad with spaces.

## Template embedding

`.env` and `docker-compose.yml` templates are embedded as `const &str` in `commands/new.rs`
using string literals. No `include_str!` from the filesystem at runtime. This keeps the binary
fully self-contained.

`docker-compose.yml` written to a new project is the **extended overlay** format (from SPECS
`docker-compose.extended.yml`), not the full base template. The base template lives in the
installed `templates/` directory.

## Error handling strategy

- `main` returns `anyhow::Result<()>`
- All commands return `anyhow::Result<()>`
- Errors are printed to stderr with `eprintln!("error: {:#}", err)` and exit code 1
- Warnings are printed to stderr with `eprintln!("warning: ...")`
- No `unwrap()` or `expect()` in production paths

## Integration test strategy

Tests live in `tests/` as Rust integration tests that invoke the compiled binary as a
subprocess via `std::process::Command`. They operate on a temporary project directory
by overriding `HOME` to a `tempdir`.

Each test file follows this pattern:
1. Build the binary path from `env!("CARGO_BIN_EXE_dev-container")`
2. Set `HOME` to a `tempdir`
3. Run binary subcommands
4. Assert on stdout/stderr content and exit codes
5. Drop tempdir (cleanup)

Docker-dependent tests (run, stop, list) are gated behind a `#[ignore]` attribute and
require a running Docker daemon. They are run explicitly with `cargo test -- --ignored`.

Non-docker tests (new, edit arg parsing, inspect file output, list empty) run in CI
without Docker.

### Test coverage targets

| Command | Without Docker | With Docker |
|---|---|---|
| `new` | name validation, force flag, idempotency, file content | — |
| `edit` | missing name error, missing project error | — |
| `inspect` | missing name, missing project, config display | — |
| `run` | missing name, invalid ssh key | start, ssh key injection |
| `stop` | missing name | stop, force, detach |
| `connect` | missing name, env parsing, default warnings | ssh invocation |
| `list` | empty table output | running/stopped status |

## Open questions / decisions for supervisor

1. **`run` post-start hooks**: The bash script installs zoxide, dotfiles, starts sshd inside
   the container after `docker compose up`. This is tightly coupled to a specific image.
   Should these hooks be preserved in the Rust rewrite, or should `run` be pure
   infrastructure (up + ssh key injection only), leaving image-level setup to the image
   entrypoint? **Recommendation: drop the hooks, make `run` pure infrastructure.**

2. **`edit -q` / container reload**: SPECS says "if `-q` is passed, do not reload the
   container, else reload container with new configuration". This implies `edit` without
   `-q` should restart the running container. This is a significant side-effect.
   Should this be implemented? **Recommendation: confirm before implementing.**

3. **`connect` user**: SSH connect needs a username. The bash script derives it from the
   container env. For `connect`, we only have the `.env` file (container may not be
   running). Should connect use the `USER` field from `.env` as the SSH username?
   **Recommendation: yes, use `USER` from `.env`, warn if missing and omit username.**

4. **Static linking**: Full musl static linking (`x86_64-unknown-linux-musl`) would make
   the binary truly portable. This requires the musl toolchain. Should the `Makefile`
   target this by default, or only offer it as an opt-in target?
   **Recommendation: opt-in `make build-static` target.**
